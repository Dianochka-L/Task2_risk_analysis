## Часть A. Бизнес-требование

### A.1. Идентификация

| Поле | Значение |
|:---|:---|
| ID | BR-RISK-PV-001 |
| Название | Отсекающее правило по первоначальному взносу (ПВ) в СПР |
| Автор | Отдел рисков |
| Приоритет | Высокий |
| Статус | На реализацию |

### A.2. Предпосылка

Ретро-портфель выдан с просрочкой 2.42% при целевом уровне 1%. Анализ показал, что
первоначальный взнос ранжирует риск дефолта не хуже действующей оценки pd (Gini 0.37 против 0.33), а порог по ПВ выводит портфель на целевую просрочку с максимальным сохранением одобрения.

### A.3. Бизнес-цель

Обеспечить уровень просрочки выдаваемого портфеля ≤ 1% при максимально возможном уровне
одобрения за счёт ввода в СПР решающего правила по ПВ.

### A.4. Функциональные требования

**Применение правила.** На шаге FULL_APPLICATION (тип запроса FULL_APPLICATION),
где значение ПВ определено, СПР обязана применять правило:
```
если initinal_payment < PV_THRESHOLD  то  заключение = DECLINE (причина = "PV_BELOW_THRESHOLD")
иначе то правило пропускает заявку дальше по стандартной логике СПР
```
**Итоговое решение** Правило работает как дополнительный отсекающий фильтр. Заявка
получает APPROVE, только если она одобрена стандартной логикой СПР И initinal_payment >= PV_THRESHOLD.
Правило не может превратить DECLINE в APPROVE.

**Параметр порога** Значение PV_THRESHOLD хранится в конфигурации СПР,
тип — число с плавающей точкой, значение по умолчанию 0.32. Изменение параметра не должно
требовать пересборки/релиза приложения.

**Граница сравнения** Сравнение строгое снизу значение, равное порогу
(initinal_payment == PV_THRESHOLD), считается прошедшим правило

**Неприменимость на раннем шаге** На шаге SHORT_APPLICATION ПВ не заполнен
(initinal_payment IS NULL) правило по ПВ на этом шаге не применяется и не влияет на
решение

**Обработка некорректного значения** Если на шаге FULL_APPLICATION
значение ПВ отсутствует (NULL) или вне допустимого диапазона (0; 1], СПР не одобряет заявку по
данному правилу и фиксирует статус ошибки данных (PV_INVALID) для разбора. Значение не
интерпретируется как 0 и не пропускается по умолчанию

**Логирование** По каждой обработанной на шаге FULL_APPLICATION заявке в БД
фиксируются: применённое значение PV_THRESHOLD, фактический initinal_payment, факт
срабатывания правила бинарный и причина отказа

### A.5. Нефункциональные требования

- Правило не увеличивает время обработки заявки более чем на 50 мс
- Изменение PV_THRESHOLD применяется без простоя сервиса

### A.6. Вне области действия

- Построение и внедрение ML-скоркарты (отдельная итерация).
- Пересмотр прочих правил СПР, из-за которых отклоняются заявки с высоким ПВ.

### A.7. Критерии приёмки

1. На выгрузке актуальных заявок при PV_THRESHOLD = 0.32 число
   одобренных заявок составляет 117 из 1000 (было 239). Проверяется скриптом 5 из queries.sql
2. Ни одна заявка с initinal_payment < 0.32 не получает статус APPROVE
3. Все заявки с initinal_payment >= 0.32, одобренные стандартной логикой, сохраняют APPROVE.
4. Изменение порога в конфигурации немедленно меняет поведение без релиза.

## Часть B. Тестовые кейсы

T = PV_THRESHOLD по умолчанию 0.32

### B.1. Функциональные (границы значения ПВ)

| ID | Предусловие | Входные данные | Ожидаемый результат |
|:---|:---|:---|:---|
| TC-01 | Заявка одобрена стандартной логикой | шаг FULL, ПВ = 0.50 (> T) | APPROVE, правило не сработало |
| TC-02 | Заявка одобрена стандартной логикой | шаг FULL, ПВ = 0.32 (= T) | APPROVE (граница включительно) |
| TC-03 | Заявка одобрена стандартной логикой | шаг FULL, ПВ = 0.3199 (чуть < T) | DECLINE, причина PV_BELOW_THRESHOLD |
| TC-04 | Заявка одобрена стандартной логикой | шаг FULL, ПВ = 0.05 (<< T) | DECLINE, причина PV_BELOW_THRESHOLD |
| TC-05 | Заявка одобрена стандартной логикой | шаг FULL, ПВ = минимально допустимое 0.006 | DECLINE, причина PV_BELOW_THRESHOLD |
